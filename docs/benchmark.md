# 匿名性能汇总

## 初始同步版本的测试方法

- 一张 L40 同时运行 Torch GPU 小模型与独立 vLLM 服务。
- MinerU 4.0.12、Torch 2.13.0+cu130、vLLM 0.29.0、Pro-2605-1.2B 原始权重。
- vLLM 显存比例 0.35、最大上下文 8192，保留默认编译、CUDA Graph 和前缀缓存。
- 客户端通过容器内 loopback 调用；所有计时请求关闭 API 结果缓存和相同请求合并，开启图片内嵌。
- 每个输入先预热。多进程对照另做一轮完整并发预热，预热不计入结果。
- 完整文档输入为三份论文（13、6、10 页）和一份中文扫描件（8 页）。每档 8 次请求，共 74 页，平均每文档 9.25 页。

这里是固定样本重复请求的热态测量。原始记录、样本、部署信息和中间文件不随仓库发布，表格只保留汇总。

## 解析档位

三份论文首页、一页扫描件和一页合成图文 PDF，每个输入计时两次，客户端并发为 1。

| 档位 | 平均秒/页 | P95 秒 | 成功请求 |
| --- | ---: | ---: | ---: |
| flash | 0.71 | 1.94 | 10/10 |
| basic | 1.78 | 2.01 | 10/10 |
| standard | 1.78 | 2.24 | 10/10 |
| advanced | 3.33 | 4.09 | 10/10 |

不同档位的结构识别和视觉语义能力不能视为等价。扫描件在 flash 下仍可能调用 OCR。这里未做标注集精度评估。

## 完整文档

以下使用单个 API 进程、每进程 2 个解析线程。每种模式累计 32 次计时请求、296 页，全部通过基本内容检查。

| 模式 | 客户端并发 | 页/秒 | 平均秒/文档 | P95 秒/文档 |
| --- | ---: | ---: | ---: | ---: |
| standard | 1 | 0.850 | 10.89 | 13.85 |
| standard | 2 | 1.119 | 16.50 | 18.06 |
| standard | 4 | 0.988 | 33.33 | 38.36 |
| standard | 8 | 1.040 | 46.12 | 70.93 |
| flash | 1 | 1.595 | 5.80 | 9.88 |
| flash | 2 | 1.572 | 10.74 | 22.71 |
| flash | 4 | 1.620 | 17.84 | 33.19 |

低负载下，standard 平均约 1.18 秒/页，flash 约 0.63 秒/页。响应时间包含排队，不能用高并发响应时间直接倒算总吞吐。

CPU ONNX 小模型对照在 standard、客户端并发 1 时为 0.346 页/秒，平均 26.71 秒/文档。改用 Torch GPU 后，同并发吞吐约为 2.45 倍；CPU 对照没有测出最优并发，不能比较两者的峰值容量。

## 进程与线程

固定 standard、客户端并发 8、相同输入和请求数量，vLLM 配置保持不变。

| API 进程 | 每进程解析线程 | 页/分钟 | 平均秒/文档 | 成功请求 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 65.6 | 40.82 | 8/8 |
| 1 | 2 | 65.8 | 42.76 | 8/8 |
| 1 | 4 | 62.9 | 53.94 | 8/8 |
| 2 | 2 | 92.0 | 29.97 | 8/8 |
| 4 | 1 | 87.7 | 32.59 | 8/8 |

增加线程没有提高这组样本的吞吐；2 进程 × 每进程 2 线程比单进程 2 线程高约 40%。两组多进程的解析线程总数均为 4，未覆盖所有配置组合；小样本中约 5% 的差异不宜解释为稳定排名。

## 瓶颈判断

现有证据不足以认定 vLLM 是主要瓶颈，更支持优先检查 API/SDK 的本地阶段与任务调度：

- vLLM 配置不变，仅增加 API 独立进程即可提高吞吐，说明 API 侧仍有可并行的工作。
- MinerU 4.0.12 的 `local_model_stage(device)` 使用设备级进程内锁，PDF 窗口准备和回填会进入该串行边界。
- 双进程测量中整张 GPU 的平均利用率约 22%，不能据此声称 GPU 已满载，也不能用这个合计指标单独定位 vLLM。

确认瓶颈需要把排队、PDF 渲染、版面分析、公式、OCR、VLM 请求和 Markdown 渲染分别计时，并关联 vLLM 的等待/运行请求数、排队时间、prefill/decode 时间和 KV 缓存占用。初始版本没有完整采集这些数据；下文给出调度版本新增的阶段观测，vLLM 内部的完整归因仍待补充。

## 统计边界

每档仅 8 或 10 次请求，P95 使用样本线性插值。前缀缓存保持开启，结果不代表任意新文档的冷态表现或长期服务容量。GPU 利用率按秒采样，不能替代内核级分析。部署前应使用实际文档分布和延迟目标做更长时间的测试。


## SQLite 调度版本：定速到达与扩容

服务 1.1.0 使用独立 CPU API 和 SQLite WAL，worker 通过 HTTP 领取任务。单 GPU 为 2 个 worker 进程 × 每进程 2 个执行线程，加 1 个 vLLM 副本；双 GPU 为两个相同解析单元。每张卡均为 L40，解析器和模型与上述环境相同。网关在 vLLM 副本之间按活跃请求数分配调用。

输入仍为 13、6、10、8 页四份文档，使用 standard、内嵌图片，关闭 API 结果缓存和内容去重。模型已预热，vLLM 前缀缓存保持开启。客户端位于 CPU API 容器内，经 loopback 发起请求；结果检查 HTTP、页数和非空 Markdown，不包含外部网络耗时。

### 12 请求的小批次

每秒提交 0.5 个请求，提交窗口 24 秒，共 111 页。

| 配置 | 成功请求 | 总耗时含排空（秒） | 页/秒含排空 | 提交窗口页/秒 | 平均响应（秒） | P95 响应（秒） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 单 GPU | 12/12 | 61.992 | 1.791 | 1.542 | 26.502 | 43.777 |
| 双 GPU | 12/12 | 41.648 | 2.665 | 1.208 | 17.719 | 24.376 |

两组均无拒绝、传输错误、客户端丢弃、失败或未完成任务。包含排空的吞吐提高约 49%；提交窗口内的吞吐受任务完成次序和窗口截断影响，这组双卡结果反而更低，不能只选单个窗口指标判断扩容效果。

### 32 请求的积压测试

每秒提交 2 个请求，提交窗口 16 秒，共 296 页。这个速率明显超过该配置对这组文档的处理能力，用于观察有界积压及排空，不是稳定负载下的延迟目标验证。

| 配置 | 成功请求 | 总耗时含排空（秒） | 页/秒含排空 | 提交窗口页/秒 | 平均响应（秒） | P95 响应（秒） | P99 响应（秒） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 单 GPU | 32/32 | 143.863 | 2.058 | 0.000 | 62.705 | 121.411 | 129.531 |
| 双 GPU | 32/32 | 86.716 | 3.413 | 0.375 | 44.801 | 70.060 | 73.379 |

两组均无拒绝、传输错误、客户端丢弃、失败或未完成任务。包含排空的吞吐提高约 66%，P95 降低约 42%。第二张卡带来收益，但未达到线性 2 倍。提交窗口只有 16 秒，多数文档在窗口结束后才完成；窗口内吞吐不能代表处理容量。尽管任务均成功，排队后的 P95 仍明显偏高，说明这个到达速率不适合作为在线低延迟服务的持续负载。

### 阶段观测

在 12 请求双卡批次中，网关计得 360 次上游调用，平均上游 HTTP 墙钟时间约 0.883 秒，平均网关准入等待约 0.032 秒。调用可以并发，不能将这些平均值相乘作为文档顺序耗时。网关等待也不包含 vLLM 内部排队。

同批次每文档阶段均值如下；公式阶段只有 9 份适用文档，其余阶段为 12 份：

| 阶段 | 平均秒/文档 |
| --- | ---: |
| SDK 总调用 | 16.663 |
| OCR 检测 | 4.271 |
| PDF 清理 | 2.802 |
| 公式 | 1.934 |
| PDF 准备 | 1.701 |
| 文字回填 | 1.134 |
| 版面 | 0.743 |
| 队列等待 | 0.549 |
| PDF 渲染 | 0.528 |
| Markdown 渲染 | 0.156 |

SDK 计时存在嵌套与重叠，不能直接相加。PDF 清理还包括共享设备锁的等待，不能把 2.802 秒全部归因于释放显存或垃圾回收。这组数据表明本地 OCR、准备、回填和锁等待仍值得优化，尚不足以认定 vLLM 是唯一或首要瓶颈。

下一步容量评估应使用实际文档分布，关闭或分开统计前缀缓存效果，并持续测量排队增长、P95/P99、worker 阶段以及 vLLM 内部排队和 KV 缓存。当前是有限批次热态测试，未证明长期稳定容量、线性扩容或任意文档的延迟保证。
